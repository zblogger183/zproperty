# Real Estate Content Ops — Status

## Data model in use
- `projects` = individual developments (new-build towers, mixed-use, plot schemes), each with a `developer_id` (a real Supabase Auth account) and `payment_plans` rows, sourced from the developer's own site/PDF where reachable rather than a broker's summary page.
- `societies` = master-planned housing schemes (DHA, Bahria Town, Al-Kabir Town, Etihad Town, etc.), each with a public profile at `/area-guide/[city]/[society]`. `projects.society_id` links a project to its society when it genuinely sits inside one — an address on an organic city neighborhood (Gulberg III, Garden Town, Johar Town, Defence Road, Bedian Road...) is correctly left `society_id: null`, that's not a gap.
- Cross-linking (added this session): the area-guide page now shows "New Projects in [Society]" (queries `projects` by `society_id`, `app/(public)/area-guide/[city]/[society]/page.tsx`); the project detail page now shows "Part of [Society] →" linking back (`app/(public)/new-projects/[slug]/page.tsx`). Before this, `projects.society_id` was populated but never rendered anywhere.

- **Fixed a real bug surfaced by this session's own earlier work**: `projects.amenities` defaulted to `'{}'` (an empty JSON *object*) at the schema level instead of `'[]'` (an empty array) — copy/paste drift in `001_schema.sql` from a different table (`societies.amenities` correctly defaults to `'[]'`). Every part of the app treats `amenities` as a `string[]`; any insert that omitted the column (a direct SQL insert, unlike the app's own forms) silently got the wrong shape. This crashed the new developer-facing `/dashboard/projects/[id]/edit` page (`.join()` on a plain object) for 4 projects inserted earlier this session without an explicit `amenities` value. - **Pending listings invisible to admins despite real listings queued**: `/admin/listings/pending` showed "0 awaiting review" while the admin dashboard's stat card correctly said "3 Pending Approval" for the same table. Root cause: `013_society_phases_blocks.sql` granted `SELECT`/`INSERT` on `society_phases`/`society_blocks` to `anon`/`authenticated` only — never to `service_role`. RLS bypass and table GRANTs are separate layers; `service_role` bypasses the RLS policies but still needs its own GRANT to touch a table at all (same root cause as the `listing_number_seq` bug fixed earlier this session). The pending-listings page embeds `phase:society_phases(name)` and `block:society_blocks(name)` via the admin (service_role) client — with no grant, the whole query errored, and the code only destructured `{ data }`, silently discarding `error` and falling back to an empty array. Fixed live + `023_society_phases_blocks_service_role_grants.sql`; also added `console.error` logging on that query so a future failure shows up in runtime logs instead of looking like "nothing pending". **Takeaway: this is the second time a table/sequence created in a later migration turned out to be missing a `service_role` grant that earlier, foundational tables already had — when adding a new table, diff its grants against an existing table's (`information_schema.role_table_grants`) rather than assuming Supabase's default privileges cover it.**

The page itself is solid (RealEstateListing schema, similar-listings, internal-linking block) — the gap is real owner/agent listings, not code. Developer *projects* are fair game to catalog from public marketing material; individual *listings* need real agent/owner-submitted inventory — do not scrape competitor portals (Zameen, Graana, etc.) to fill this in, that would be misappropriating their content.
3. **Societies admin form still has no phases/blocks management UI** (the `society_phases`/`society_blocks` tables from migration 013 are still agent-extensible-only, populated via the listing form's "add new" flow) and no lat/lng map picker (image upload and edit page are done, see above).
4. **`cities.listing_count` / `areas.listing_count` / `societies.listing_count` are all the same kind of dead stored-counter column** (`DEFAULT 0`, no trigger) — only `get_public_stats()`'s cities figure has been fixed to bypass it (via a live UNION query) so far; anywhere else in the codebase still reading `.listing_count` directly off these tables is reading a stale/frozen number, not a real one.
5. **Developer dashboard has no Analytics/CRM/Subscription/Boost Center equivalents** — those stayed agent-only nav items; developers only got Dashboard, My Projects, Add Project, Lead Inbox, Settings. Also no bulk-edit or duplicate-project-from-existing flow, and a developer can't manage `payment_plans` display order (always insert order = form order).

## Conventions established this session
- Never attribute a project to a marketing/broker site (AIWA, Titanium Agency, Sky Marketing, etc.) as its developer — find the real builder and cross-check via the developer's own site or 2+ independent sources before writing `developer_id`.
- Reuse an existing developer account if the project belongs to a company already in the DB. Don't create duplicate accounts for spelling variants of the same company (e.g. "RealTek Developers" / "Realtek Properties" / "RealTech Properties" is one developer, not three).
- New developer accounts: real Supabase Auth users (`crypt()`/pgcrypto bcrypt, pre-confirmed email), `{slug}@zproperty.pk` placeholder email, sequential `+9230000001xx` placeholder phone (check `SELECT phone FROM users WHERE phone LIKE '+92300000%' ORDER BY phone` for the next free one), random 12-char password. Credentials are shown once in chat only — not recoverable after — so the user needs to save them immediately.
- Never fabricate pricing, unit sizes, or dates that aren't published anywhere. Leave the field null and say so in the description, rather than estimate.
